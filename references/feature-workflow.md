# Feature 流程

加功能：**触点竖切 → 最小可交付 → 兼容与回归**。Map 未 complete（且非合法 fast path）禁改业务代码。

## 闸门顺序

```
Map complete → 触点清单 → 选最小竖切 → 对齐仓规 → 边界内实现 → 验证 ≥ L1 → 记兼容风险 → Leave
```

## 1) 触点清单（竖切前）

从 Map 列出实现该行为所需全部触点，至少覆盖会碰到的层：

| 层 | 例子 |
|----|------|
| 入口 | API / UI / CLI / 定时任务 |
| 编排 | controller / usecase / 中间件 |
| 数据 | repo / schema / 缓存键 |
| 配置 | 开关、权限、环境变量 |
| 调用方 | 已有客户端、批任务、测试 |

触点进 Map **触点列表**；不在边界内的标为「本任务不做」并写进 **改动边界**。

## 2) 最小竖切

- 优先能满足 `task.md` **成功标准**的**一条**端到端路径（非一次铺完全部周边）
- 「竖切」= 入口→存储→返回都打通的最小切片；周边兼容可列为 follow-up（须在 Map/notes 写明）
- 对齐仓内既有模式：命名、错误处理、测试布局、特性开关习惯

**禁止**：无竖切计划就横向扫仓「相关文件都改一点」。

## 3) 兼容风险（必想）

实现前/后在 `change.md` 或 `notes.md` 点名：

| 风险 | 要问的 |
|------|--------|
| 调用方 | 旧客户端/旧字段是否仍可用？ |
| 数据 | 要不要迁移、默认值、双写？ |
| 开关 | 能否特性开关 / 灰度？不能则回滚点是什么？ |
| 权限 / 多租户 | 新路径是否绕过旧校验？ |

有破坏性变更却未写风险 → 不得宣称 done。

## 4) 回归要点

宣称完成前至少覆盖：

- [ ] 成功标准对应的新路径（主竖切）
- [ ] Map 影响面里点名的旧路径冒烟（防误伤）
- [ ] （若有）开关关闭时行为与改前一致
- [ ] （可选）构建 / lint / 仓规测试命令

## 5) 证据等级（feature）

| 等级 | feature 含义 | 可宣称完成？ |
|------|--------------|--------------|
| L0 | 只说「加上了」无步骤 | **否** |
| L1 | 手工步骤：新路径成功 + 关键旧路径未炸 | **是**（默认最低） |
| L2 | 自动化测试覆盖新行为（及必要回归） | **是**（优选） |

`change.md`：**改动摘要** + **验证**（步骤 / 前 / 后）。非 refactor，禁顺手大重构。

## 6) Change 检查清单（短）

- [ ] 触点与边界在 Map 中齐全
- [ ] 本次 diff = 一条最小竖切（或用户明确批准的更大范围）
- [ ] 兼容风险已记录
- [ ] 新路径 + 关键旧路径已验证；证据 ≥ L1

## 失败兜底

| 触发 | 处理 |
|------|------|
| 成功标准模糊 | Orient 追问；勿在 Map draft 时改码 |
| 竖切发现必须改无关模块 | 更新边界，**🔴 检查点**问用户 |
| 只能破坏性上线且无回滚 | `blocked` 或要求开关/迁移方案 |
| 想顺手重构周边 | 停手；另开 refactor 任务 |
